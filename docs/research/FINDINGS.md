## R2/R3 — RAG state of the art

| Finding | Evidence | → Action |
|---|---|---|
| **Contextual Retrieval**: prepend a 50–100-token, LLM-written context to each chunk before indexing. Contextual embeddings cut retrieval failures 35%; adding contextual BM25 cuts them 49%; adding reranking cuts them 67%. Passing the top-20 chunks works best. With prompt caching it costs about $1.02 per million document tokens. | [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval) | `agentkit ingest --contextualize` (live mode): whole document in a cached system prompt, one short context per chunk. |
| **Hybrid search + RRF**: fuse keyword and vector rankings by rank, not score: `RRF(d)=Σ 1/(k+rank)`, with k≈60. Score fusion is biased because BM25 and cosine scores sit on different scales. | [BigData Boutique on RRF](https://bigdataboutique.com/blog/reciprocal-rank-fusion-how-it-works-and-when-to-use-it), [Mixpeek guide](https://mixpeek.com/guides/hybrid-search-fusion-rrf-score-normalization) | Add RRF fusion over several retrievers: word BM25 + **character n-grams** (no dependencies, robust to Arabic morphology and Franco-Arabic spelling) + optional dense embeddings. |
| **Native citations**: `search_result` content blocks (`source`, `title`, `content[]`, `citations:{enabled:true}`; citations are off by default and must use the same setting across all results). The response carries `search_result_location` citations with `search_result_index`, `start_block_index`, `end_block_index` and `cited_text`. Supported on all active models except Haiku 3; no beta header. | [Claude docs: Search results](https://platform.claude.com/docs/en/build-with-claude/search-results) | Replace our regex `[n]` parsing in live mode with API citations. Citations become verifiable and cannot point to a document that wasn't supplied. |

## R4 — Arabic retrieval

| Finding | Evidence | → Action |
|---|---|---|
| A systematic Arabic RAG study found **sentence-aware chunking** beats the other segmentation methods. **BGE-M3** (70.99) and **multilingual-e5-large** (70.31) were the best embedders, ahead of Arabic-only models. The **bge-reranker-v2-m3** reranker "significantly boosts faithfulness" on complex datasets. Scored with RAGAS (context precision/recall, faithfulness, answer relevancy). | [arXiv 2506.06339](https://arxiv.org/abs/2506.06339) (via search extract) | Chunk on sentence boundaries, including Arabic `؟ ؛ ۔` and `.!?`. Optional `[dense]` extra defaults to `BAAI/bge-m3`; optional `[rerank]` extra uses `BAAI/bge-reranker-v2-m3`. |
| **Light stemming** (strip prefixes and suffixes, no root extraction) is the standard, competitive choice for Arabic IR (Larkey et al., *Light10*). | [UMass CIIR: Improving Stemming for Arabic IR](https://ciir-publications.cs.umass.edu/pub/web/getpdf.php?id=249), [PMC study on Arabic stemmers](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8156998/) | Replace our article-only stripper with a Light10-style stemmer (prefixes و ال بال كال فال لل; suffixes ها ان ات ون ين يه ية ه ة ي). |
| Franco-Arabic has no standard; the common digit conventions are 2=ء, 3=ع, 5=خ, 6=ط, 7=ح, 8=غ/ق, 9=ق/ص. Rule-based candidate generation is the usual first step. | [ArabiziKit](https://huggingface.co/rabeeeehh/arabizi-kit-model), [arXiv 1808.03437](https://arxiv.org/abs/1808.03437v1) | Add rule-based Franco-Arabic→Arabic candidate transliteration for query expansion. Character n-grams tolerate the imperfect spellings it produces. |
| Gap found by our own testing: Arabic-Indic digits (١٥) don't match Western digits (15), and NFKC doesn't map them. | Local test | Normalise ٠–٩ and ۰–۹ to 0–9. Also map Persian ی ک to ي ك. |

## R5 — Arabic OCR

| Finding | Evidence | → Action |
|---|---|---|
| **KITAB-Bench** (8,809 samples, 9 domains): vision-language models beat traditional OCR (EasyOCR, PaddleOCR, Surya) by about **60% CER** on average. Best CER: Gemini-2.0-Flash 0.13, AIN-7B 0.20, GPT-4o 0.31. Common failure points are numerals, word elongation (tatweel) and tables. | [arXiv 2502.14949](https://arxiv.org/abs/2502.14949v1) (via search extract) | Keep a vision LLM (Claude) as the default OCR engine. Post-process: remove tatweel, normalise digits, keep tables as Markdown. |
| Open-source: **QARI-OCR v0.2** (Qwen2-VL-2B fine-tune) has CER 0.061 / WER 0.160 on diacritised text. **Arabic PP-OCRv6** beats Tesseract and vanilla PaddleOCR on CPU. | [QARI-OCR paper](https://huggingface.co/papers/2506.02295), [arabic_PP-OCRv6](https://huggingface.co/medyas/arabic_PP-OCRv6_small_rec) | Document the engine choice by cost tier in `ocr-document-engineer`: Claude vision → QARI (GPU, local) → PaddleOCR Arabic (CPU) → Tesseract (last resort). Add an OCR quality heuristic that flags pages for re-OCR. |
